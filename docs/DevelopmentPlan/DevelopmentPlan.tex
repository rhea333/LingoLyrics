This document outlines the Development Plan for \progname{} (\textbf{LingoLyrics}), a multi-platform language-learning ecosystem that bridges interactive song playback with structured language instruction. This report covers project governance, workflow and repository strategies, continuous integration pipelines, schedule breakdowns, risk management for our Proof of Concept (PoC), technology stack selections, and team operational charters.

There is no confidential information associated with this project. LingoLyrics is an open-source capstone project operating without corporate non-disclosure agreements, proprietary industry datasets, or commercial restrictions.

There is no proprietary intellectual property (IP) to protect. All application code, file format specifications (song map schema), system documentation, and design assets will be developed openly under standard university capstone guidelines.

\section{Workflow Plan}

To maintain high code health and release reliability, our engineering pipeline integrates automated continuous testing via GitHub Actions. Every pull request triggers CI jobs that execute unit test suites, run static analysis using \texttt{ESLint} (enforcing Airbnb TypeScript standards), and validate song-map JSON schema integrity. Branch protection rules strictly mandate that all status checks pass and at least one peer approval is logged before changes can be integrated.

\vspace{1em}

Software development and project maintenance will be coordinated using GitHub for version control and issue management. All team activities, ranging from feature implementation to supervisor action items, are tracked through centralized issues. The scope of tracked work encompasses:
\begin{itemize}
    \item Core Feature \& Interface Engineering
    \item Automated Test Suite Construction
    \item Deliverable Compilation \& Submission
    \item CI/CD Pipeline \& Cross-Platform Target Configuration
    \item Defect Remediation \& Bug Fixes
    \item Advisor Feedback Implementation
    \item Regular Synchronizations \& Architecture Reviews
\end{itemize}

\section{Proof of Concept Demonstration Plan}

The purpose of the Proof of Concept (PoC) plan is to outline how our team will validate the feasibility of LingoLyrics by testing and resolving its most critical technical risks prior to full system development.

\subsection{Objective}

The objective of our PoC is to demonstrate the technical feasibility of real-time audio-lyric synchronization, multi-language text segmentation, and direct flashcard export. The PoC does not need to deliver a fully styled end-to-end consumer application; rather, it should validate that the underlying timing, NLP tokenization, and export workflows operate reliably enough to justify full system implementation.

\subsection{Scope of PoC}

\begin{itemize}
    \item \textbf{Core Deliverables:} A functional prototype that:
    \begin{itemize}
        \item Plays back an audio track while maintaining sub-second, real-time highlighting of corresponding lyric lines across desktop and mobile browsers.
        \item Accurately parses non-Latin or unspaced text (e.g., Japanese Kanji/Kana or Vietnamese) into interactive words with corresponding transliteration/romanization.
        \item Generates and transmits a serialized vocabulary package (including target word, definition, and context sentence) directly into a local or remote Anki instance.
    \end{itemize}

    \item \textbf{Exploratory Nature:}
    \begin{enumerate}
        \item Evaluating cross-platform web audio timing APIs to achieve reliable sub-second synchronization latency.
        \item Comparing language-specific tokenization pipelines for accurate segmentation of non-spaced scripts.
        \item Testing seamless integration methods with Anki (e.g., AnkiConnect API versus custom file payloads).
    \end{enumerate}

    \item \textbf{Not Included:} Complete user account management, custom UI design/styling, broad catalog expansion, or cloud sync backends.
\end{itemize}

\section{Expected Technology}

We expect to use \textbf{TypeScript} as our primary programming language across the client application and backend service integration, ensuring type safety and code reusability. Python or Go may be utilized for backend microservices or specialized text processing tasks.

\vspace{1em}

For application development, we plan to use \href{https://reactnative.dev/}{\textbf{React Native}} with \href{https://expo.dev/}{\textbf{Expo}} (or \textbf{Electron/React} for desktop targets) to build a responsive, cross-platform user interface. For language processing, we will integrate specialized text segmentation tools such as \texttt{kuromoji.js} or \texttt{Sudachi} to handle word tokenization, furigana generation, and romanization of non-Latin scripts.

\vspace{1em}

Audio timing and synchronized lyric rendering will be handled using platform-agnostic playback engines such as \href{https://howlerjs.com/}{\textbf{Howler.js}} or the native Expo Audio API, capable of sub-second timekeeping precision.

\vspace{1em}

We will use \href{https://eslint.org/}{\textbf{ESLint}} and \href{https://prettier.io/}{\textbf{Prettier}} to enforce consistent code formatting and coding standards, managed locally via \textbf{Husky} pre-commit hooks.

\vspace{1em}

Testing will be conducted using \href{https://jestjs.io/}{\textbf{Jest}} for unit and integration tests, alongside \textbf{istanbul/nyc} or built-in coverage tools to measure test completeness.

\bigskip
\noindent\textbf{CI/CD \& Version Control:} We will use \textbf{Git}, \textbf{GitHub}, and \textbf{GitHub Projects} for version control, issue tracking, and sprint management. Continuous Integration (CI) pipelines will be executed via \textbf{GitHub Actions} to run automated test suites, lint checks, and cross-platform build verifications on every pull request.

\section{Use of AI and LLMs}

\begin{itemize}
    \item \textbf{Code Development:} AI tools (e.g., GitHub Copilot, ChatGPT) will be utilized as programming assistants for generating boilerplate code, routine utility functions, and regular expressions for text parsing.
    \item \textbf{Documentation \& Quality Assurance:} LLMs will be used exclusively for proofreading documentation—identifying grammatical errors, resolving text parsing inconsistencies, and ensuring proper LaTeX syntax formatting—as well as suggesting candidate unit test scenarios.
    \item \textbf{Verification Protocol:} No AI-generated code or text modifications will be integrated directly without human verification. All outputs must undergo thorough manual peer review, adhere to project linting standards, and pass automated unit test suites prior to being merged.
\end{itemize}

\section{Coding Standard}

All codebase components will strictly follow the **Airbnb JavaScript/TypeScript Style Guide**. Adherence will be automatically enforced via \texttt{ESLint} pre-commit hooks and status checks in GitHub Actions.

\section*{Appendix --- Reflection}

\begin{enumerate}
    \item Why is it important to create a development plan prior to starting the project?

    Creating a development plan prior to starting the project encourages the team to establish collaboration practices, align expectations, and identify technical risks early before writing code. It sets clear guidelines for communication, Git workflows, coding standards, and project scheduling, which significantly reduces misunderstandings and integration friction later. A comprehensive plan also provides a shared reference for team roles, decision-making protocols, and toolchains. By agreeing on these foundational practices upfront, the team saves time, prevents scope creep, and can focus directly on executing technical milestones such as real-time audio synchronization and multi-language tokenization.

    \item In your opinion, what are the advantages and disadvantages of using CI/CD?

    \textbf{Advantages:} CI/CD enforces coding standards automatically from day one. Automated build and test workflows instantly catch syntax errors, broken dependencies, and failing component logic before pull requests reach the main branch. It maintains a stable codebase, streamlines peer reviews through automated linting checks, and provides fast feedback on overall project health across diverse development environments.

    \textbf{Disadvantages:} Pipeline configuration and maintenance require non-trivial setup time and technical overhead. Continuous integration scripts can slow down rapid prototyping if builds become slow or flaky. Furthermore, CI/CD is only as reliable as the underlying test suite; maintaining comprehensive test coverage demands ongoing team effort, and build runners can introduce minor resource bottlenecks during tight delivery windows.

    \item What disagreements did your group have in this deliverable, if any, and how did you resolve them?

    While organizing the Proof of Concept (PoC) plan and overall development strategy, our team had two key technical debates:
    \begin{itemize}
        \item \textbf{Target Platform (Web Application vs. Native Mobile App):} We debated whether to focus initial development on a web-based app or a native mobile application. The core issue was balancing low-latency, sub-second audio sync across platforms with team implementation bandwidth. We resolved this by agreeing on a web-first architecture that prioritizes cross-browser media timing APIs, while leaving mobile-responsive layout options open for expansion.
        \item \textbf{Primary Target Audience (Focused/Serious vs. Casual Learners):} We had differing views on whether the app should cater to "sit-down" power users (who require deep grammar breakdowns, detailed segment tokenization, and direct Anki flashcard export) versus casual, on-the-go language learners. We resolved this by prioritizing serious self-directed learners as our primary persona for the PoC scope, while keeping the user interface clean and accessible enough for casual listening.
    \end{itemize}
\end{enumerate}

\section*{Appendix --- Team Charter}

\subsection*{External Goals}
The team's main goal is to create an engaging, accessible tool that bridges music consumption and language acquisition. Through LingoLyrics, we aim to strengthen our technical capabilities in cross-platform web audio engineering, multi-language NLP tokenization, and third-party workflow integrations like Anki. We also hope to deliver a polished, technically rigorous project that stands out at the Capstone EXPO, serves as a strong portfolio piece for full-stack software development, and earns recognition from judges and peers.

\subsection*{Attendance}

\subsubsection*{Expectations}
The team expects all members to attend scheduled syncs and arrive on time. If a member is unable to attend or will be late, they are expected to notify the team in Discord ahead of time, review the recorded meeting notes, and provide an async status update on their assigned tasks. Prior to each meeting, the meeting chair will share an agenda outlining key discussion points (e.g., audio engine performance, map editor features, SRS integration). Meetings will end early if all agenda topics are resolved, or continue asynchronously in Discord if further technical discussion is needed.

\subsubsection*{Acceptable Excuse}
An acceptable excuse for missing a meeting is an unpredictable personal emergency, illness, or documented academic exam conflict communicated ahead of time. Missing meetings due to poor time management or avoidable scheduling conflicts is unacceptable.

For project deliverables, acceptable excuses include unforeseen personal emergencies or severe technical blockers that were proactively flagged to the group. Unacceptable excuses include underestimating task complexity, poor time planning, or neglecting assigned components until right before deadline dates. We value transparency and expect everyone to communicate potential delays early so the team can adjust task allocations.

\subsubsection*{In Case of Emergency}
Team members must notify the group via Discord as soon as practically possible during an emergency. For occasional occurrences, team members will redistribute critical tasks (such as urgent PR reviews or deliverable sections) to keep project development moving forward. However, if a member experiences repeated issues meeting deadlines, the team will schedule a check-in to re-balance responsibilities or consult course instructors if necessary.

\subsection*{Accountability and Teamwork}

\subsubsection*{Quality} 
Deliverables and codebase additions must meet Level 4 standard criteria on project rubrics. Code merged into main branches must pass automated CI linting checks, unit tests, and receive approval from a designated peer reviewer. If team members encounter unfamiliar domain concepts—such as complex foreign text tokenizers or cross-platform web audio APIs—they are expected to research solutions independently and consult team members to maintain high technical standards.

\subsubsection*{Attitude}
Team members must maintain a professional, supportive, and open-minded attitude. Feedback during pull request reviews or planning sessions should remain constructive and focused on code quality and project objectives rather than personal preferences.

\subsubsection*{Stay on Track}
Each team member is accountable for completing assigned GitHub issues within sprint timeframes. Work progress will be tracked transparently using GitHub Projects and commit histories. If someone anticipates falling behind on a task, they must flag it early in Discord so workload can be shared. Individual contributions will be regularly reviewed through issue completion and active participation in code reviews to ensure equitable workloads.

\subsubsection*{Team Building}
Our team will hold regular in-person meetings each week to foster strong working relationships. We also plan to dedicate brief informal time before sprint planning sessions and organize monthly team social activities to maintain high team morale and open communication.

\subsubsection*{Decision Making} 
Decisions will be made through technical consensus following research and discussion of trade-offs. If the team reaches an impasse on architectural choices (e.g., platform targets or language tokenization libraries), members will present brief technical comparisons, consult with project advisors if needed, and conduct a formal team vote to reach a binding decision.
