This document outlines the Development Plan for \progname{}, a song-based language-learning product consisting of a mobile learner application and a web-based song-map editor for content creators. It covers project governance, workflow and repository strategy, continuous integration, scheduling, the Proof of Concept (PoC) plan and its risks, technology choices, and the team charter.
 
\section{Confidential Information?}

There is no confidential information associated with this project. LingoLyrics is an open-source capstone project operating without corporate non-disclosure agreements, proprietary industry datasets, or commercial restrictions.

\section{IP to Protect}

There is no proprietary intellectual property (IP) to protect. All application code, file format specifications (song map schema), system documentation, and design assets will be developed openly under standard university capstone guidelines.

\section{Copyright License}

The software source code, map schema definitions, and associated documentation will be distributed under the \textbf{MIT License}. This choice ensures maximum accessibility for community contributors and map creators while permitting open integration with third-party tools.

\section{Team Meeting Plan}

Meetings will be conducted using a hybrid approach, leveraging specific virtual channels and in-person sessions during scheduled capstone periods.

\begin{itemize}
    \item \textbf{Internal Team Meetings:} Held virtually every Friday from 11:00 AM to 12:00 PM via Discord or Google Meet to review project progress, manage sprint planning, assign issues, and resolve technical blockers.
    \item \textbf{Supervisor Meetings:} Held periodically on Fridays from 10:00 AM to 10:30 AM via Microsoft Teams with our supervising professor, Dr.~Angela Zavaleta Bernuy, to present milestone deliverables, track progress, and receive guidance.
    \item \textbf{Meeting Structure:} Meeting operational roles will rotate among team members each session:
    \begin{itemize}
        \item The meeting chair posts the agenda as a GitHub issue using the meeting issue template at least 24 hours before the meeting.
        \item Agenda topics are written as questions, each with a time estimate and the member responsible for leading it.
        \item The first item is always a review of the agenda and meetings last at most one hour.
        \item Meetings end with a written list of decisions and each member's action items, recorded in the same issue by the minute-taker, along with attendance.
    \end{itemize}
\end{itemize}

\section{Workflow Plan}

\subsection{Branching}
\begin{itemize}
    \item \texttt{main} always contains the latest submitted state of the
    project. It is protected: changes arrive only through pull requests that
    pass CI and have at least one approving review.
    \item \texttt{develop} is the integration branch. Feature branches are
    created from \texttt{develop} and merged back into it. We keep this branch
    so that \texttt{main} only changes at submission points.
    \item Before each deliverable deadline, \texttt{develop} is merged into
    \texttt{main} through a release pull request reviewed by the QA manager.
    \item Each submission is tagged on \texttt{main}, for example
    \texttt{PS-DevPlan-Rev0}, \texttt{SRS-Rev0}, and \texttt{PoC-Demo}. Revision 0
    and Revision 1 are distinguished by tags rather than separate files.
    \item Pull requests are squash-merged and reference their issue with
    \texttt{Closes \#N} so issues close automatically with a link to the merge.
    Work done in pairs uses GitHub co-author commit trailers.
\end{itemize}

\subsection{Issues, Milestones, and Pull Requests}
\begin{itemize}
    \item Issues are created from templates: the capTemplate meeting, lecture,
    and supervisor templates, plus our own feature/bug template that requires a
    summary, acceptance criteria (the Definition of Done), an owner, a reviewer,
    and linked dependencies.
    \item Issues are sized to be completed by one person in a few hours. Large
    items such as ``write SRS'' are split into one issue per section.
    \item Each course deliverable is a GitHub milestone with its due date, and
    every issue is assigned to a milestone.
    \item A pull request template asks the author to confirm tests and lint
    pass, link the issue, and list any AI-assisted changes.
    \item Deliverable checklists from the course repository are copied into the
    deliverable's issue and ticked off by the QA manager.
\end{itemize}

\subsection{Continuous Integration}
GitHub Actions runs on every pull request and on pushes to \texttt{main}:
\begin{itemize}
    \item build the \LaTeX{} documents to PDF (provided by capTemplate) and
    publish them to GitHub Pages; generated files are not committed;
    \item run \texttt{ESLint} and \texttt{Prettier} checks;
    \item run the \texttt{Jest} unit test suite with a coverage report;
    \item validate all example song maps against the shared JSON Schema.
\end{itemize}
A pull request cannot be merged into \texttt{develop} or \texttt{main} unless
all checks pass.

\section{Proof of Concept Demonstration Plan}

The PoC demonstration will show that the three riskiest parts of \progname{}
can be built with our chosen technology before we commit to full development.
It is a narrow technical demonstration, not a prototype of the finished product:
it uses one test phone, one short song per language, and no user interface
styling.

\subsection{Objective}

The objective of our PoC is to demonstrate the technical feasibility of real-time audio-lyric synchronization, multi-language text segmentation, and direct flashcard export. The PoC does not need to deliver a fully styled end-to-end consumer application; rather, it should validate that the underlying timing, NLP tokenization, and export workflows operate reliably enough to justify full system implementation.

\subsection{Scope of PoC}

\begin{itemize}
    \item \textbf{Core Deliverables:} A functional prototype that:
    \begin{itemize}
        \item Plays back an audio track while maintaining sub-second, real-time highlighting of corresponding lyric lines across desktop and mobile browsers.
        \item Accurately parses non-Latin or unspaced text (e.g., Japanese Kanji/Kana or Vietnamese) into interactive words with corresponding transliteration/romanization.
        \item Generates and transmits a serialized vocabulary package (including target word, definition, and context sentence) directly into a local or remote Anki instance.
    \end{itemize}

    \item \textbf{Exploratory Nature:}
    \begin{enumerate}
        \item Evaluating cross-platform web audio timing APIs to achieve reliable sub-second synchronization latency.
        \item Comparing language-specific tokenization pipelines for accurate segmentation of non-spaced scripts.
        \item Testing seamless integration methods with Anki (e.g., AnkiConnect API versus custom file payloads).
    \end{enumerate}

    \item \textbf{Not Included:} Complete user account management, custom UI design/styling, broad catalog expansion, or cloud sync backends.
\end{itemize}

\subsection{Risks}

Table~\ref{TblRisks} lists the implementation risks that most threaten the
project.

\begin{table}[h!]
\caption{PoC Risks} \label{TblRisks}
\begin{tabularx}{\textwidth}{lX}
\toprule
\textbf{Risk} & \textbf{Why it is a concern}\\
\midrule
R1: Lyric sync on a phone & Mobile audio playback may not report its position often or accurately enough to keep lyric highlighting within 0.5 seconds of the audio, which the synchronized playback goal requires.\\
R2: Segmenting lyrics & Tokenizers are built for standard prose; lyrics contain slang, fragments, and mixed scripts. The Japanese dictionary is also large and may load too slowly on a phone.\\
R3: Anki from a phone & AnkiConnect only works with desktop Anki. It is unclear whether the mobile app can add notes to a learner's Anki collection directly (for example, through the AnkiDroid API) or must use an export file.\\

\subsection{What We Will Demonstrate}
Each item addresses one risk and has a pass criterion.
\begin{itemize}
    \item \textbf{R1:} Play a test song on the test phone with line-by-line
    highlighting driven by a song map. The app logs the playback position at
    each line change. \emph{Pass:} at least 95\% of line changes occur within
    0.5 seconds of their mapped timestamps.
    \item \textbf{R2:} Open a Japanese test song and display each lyric line
    as selectable words with romanization. \emph{Pass:} at least 90\% of words
    in 20 test lines match a segmentation checked by the team, and the lesson is
    ready within 3 seconds of opening.
    \item \textbf{R3:} Select a word in the app and send it to Anki.
    \emph{Pass:} a note with the term, translation, and context sentence
    appears in a test deck, using at least one of the candidate methods.
\end{itemize}

\textbf{Not included:} user accounts, visual design, the song-map editor
interface (maps are written by hand for the PoC), cloud sync, and more than one
song per language.

\subsection{If the PoC Fails}
If a risk is not resolved by the demonstration, we will discuss redefining the
scope with our supervisor and the instructor. Likely directions are:
\begin{itemize}
    \item \textbf{R1:} highlight lyrics at a coarser tolerance, or use a native
    audio module instead of the Expo audio library.
    \item \textbf{R2:} compute segmentation in the editor and store it in the
    song map, where the creator verifies it, rather than segmenting on the
    phone.
    \item \textbf{R3:} replace direct sending with an export file that the
    learner imports into Anki, and revise the vocabulary handoff goal.
\end{itemize}

Each component owner in Table~\ref{TblRoles} demonstrates the risk for their
component. The demonstration runs on one team member's phone, mirrored to a

\section*{Appendix --- Reflection}

\begin{enumerate}
    \item Why is it important to create a development plan prior to starting the project?

    Writing the plan forced us to make decisions we had been postponing. For
    example, writing the technology section exposed that half of our drafts
    assumed a web app while the Problem Statement described a phone app, and
    writing the PoC plan made us admit that we did not know whether Anki can be
    reached from a phone at all. Finding these gaps now costs a conversation;
    finding them in February would cost rewritten code. The plan also gives us
    agreed rules (branch names, review requirements, charter triggers) that we
    can point to instead of arguing case by case.

    \item In your opinion, what are the advantages and disadvantages of using CI/CD?

    \textbf{Advantages:} CI checks every pull request the same way, so lint
    errors, failing tests, and invalid song maps are caught before they reach
    \texttt{develop}. This matters for us because the editor and the learner
    app both depend on the same song-map format: a schema check in CI catches a
    change that would silently break the other component. CI also builds our
    PDFs automatically, so the submitted documents always match the source.

    \item What disagreements did your group have in this deliverable, if any, and how did you resolve them?

    While organizing the Proof of Concept (PoC) plan and overall development strategy, our team had two key technical debates:
    \begin{itemize}
        \item \textbf{Target platform (web vs.\ mobile):} some members preferred
        a web application because browser audio APIs are familiar and one
        codebase would reach every device. Others argued that learners mostly
        listen to music on their phones with headphones. We resolved this by
        splitting by user: the learner experience is a mobile app, while the
        creator editor is web-based, because precise timing work needs a large
        screen. Both share one song-map format.
        \item \textbf{Primary audience (serious vs.\ casual learners):} we
        disagreed about whether to design for learners who want detailed word
        breakdowns and Anki export, or for casual listeners. We chose
        self-directed serious early learners as the primary audience for
        our goals and PoC, while keeping the interface simple enough for casual
        use.
    \end{itemize}
\end{enumerate}

\section*{Appendix --- Team Charter}

\subsection*{External Goals}
The team's main goal is to create an engaging, accessible tool that bridges music consumption and language acquisition. Through LingoLyrics, we aim to strengthen our technical capabilities in cross-platform web audio engineering, multi-language NLP tokenization, and third-party workflow integrations like Anki. We also hope to deliver a polished, technically rigorous project that stands out at the Capstone EXPO, serves as a strong portfolio piece for full-stack software development, and earns recognition from judges and peers.

\subsection*{Attendance}

\subsubsection*{Expectations}
The team expects all members to attend scheduled syncs and arrive on time. If a member is unable to attend or will be late, they are expected to notify the team in Discord ahead of time, review the recorded meeting notes, and provide an async status update on their assigned tasks. Prior to each meeting, the meeting chair will share an agenda outlining key discussion points (e.g., audio engine performance, map editor features, SRS integration). Meetings will end early if all agenda topics are resolved, or continue asynchronously in Discord if further technical discussion is needed.

\subsubsection*{Acceptable Excuse}
An acceptable excuse for missing a meeting is an unpredictable personal emergency, illness, or documented academic exam conflict communicated ahead of time. Missing meetings due to poor time management or avoidable scheduling conflicts is unacceptable.

For project deliverables, acceptable excuses include unforeseen personal emergencies or severe technical blockers that were proactively flagged to the group. Unacceptable excuses include underestimating task complexity, poor time planning, or neglecting assigned components until right before deadline dates. We value transparency and expect everyone to communicate potential delays early so the team can adjust task allocations.

\subsubsection*{In Case of Emergency}
Team members must notify the group via Discord as soon as practically possible during an emergency. For occasional occurrences, team members will redistribute critical tasks (such as urgent PR reviews or deliverable sections) to keep project development moving forward. However, if a member experiences repeated issues meeting deadlines, the team will schedule a check-in to re-balance responsibilities or consult course instructors if necessary.

\subsection*{Accountability and Teamwork}

\subsubsection*{Quality} 
Deliverables and codebase additions must meet Level 4 standard criteria on project rubrics. Code merged into main branches must pass automated CI linting checks, unit tests, and receive approval from a designated peer reviewer. If team members encounter unfamiliar domain concepts—such as complex foreign text tokenizers or cross-platform web audio APIs—they are expected to research solutions independently and consult team members to maintain high technical standards.

\subsubsection*{Attitude}
Team members must maintain a professional, supportive, and open-minded attitude. Feedback during pull request reviews or planning sessions should remain constructive and focused on code quality and project objectives rather than personal preferences.

\subsubsection*{Stay on Track}
\textbf{Triggers.} Any of the following starts the process below:
\begin{itemize}
    \item attendance below 90\% in a term, or two unexcused absences;
    \item an assigned task more than 48 hours past its due date without prior
    notice;
    \item no commits, reviews, or closed issues for two consecutive weeks;
    \item missing the internal 48-hour deadline for a deliverable section.
\end{itemize}

\textbf{Consequences.} Each step applies if the previous one does not resolve
the problem within one week:
\begin{enumerate}
    \item A private check-in with the project lead to understand the cause and
    agree on a plan.
    \item Discussion at a team meeting, recorded in the meeting issue, with
    specific tasks and dates.
    \item The member's tasks are reassigned, and the situation is reflected
    honestly in the Team Contribution Survey.
    \item The issue is raised with our TA, and then with the instructor.
\end{enumerate}

\textbf{Rewards.} After each demonstration, the team goes out for a meal
together. A member who closes the most issues in a milestone chooses the
restaurant.

\subsubsection*{Team Building}
Our team will hold regular in-person meetings each week to foster strong working relationships. We also plan to dedicate brief informal time before sprint planning sessions and organize monthly team social activities to maintain high team morale and open communication.

\subsubsection*{Decision Making} 
Decisions will be made through technical consensus following research and discussion of trade-offs. If the team reaches an impasse on architectural choices (e.g., platform targets or language tokenization libraries), members will present brief technical comparisons, consult with project advisors if needed, and conduct a formal team vote to reach a binding decision.
