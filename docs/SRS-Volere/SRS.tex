\section*{About This Document}

This document specifies the requirements for \progname{}, a language
learning product based on songs. It is written for the development team, who
will design, build, and test the product from it, for new team members who
need to get up to speed, and for the supervisor, teaching staff, and peer
reviewers who assess it. A reader outside the team should be able to design
and test the product from this document, the Problem Statement, and the
Hazard Analysis alone.

\subsection*{Notation and Conventions}

\begin{itemize}
  \item \textbf{Requirement identifiers.} Every requirement has a unique
        identifier made of a prefix and a number. The prefixes are MC
        (mandated constraint), FR (functional), LF (look and feel), UH
        (usability and humanity), SL (speed and latency), PA (precision or
        accuracy), RB (robustness), CP (capacity), SC (scalability), LO
        (longevity), OE (operational and environmental), MS (maintainability
        and support), CU (cultural), and ST (standards). The prefixes HS
        (health and safety), AC (access), IN (integrity), PR (privacy), AU
        (audit), IM (immunity), and LG (legal) are shared with the Hazard
        Analysis, so each safety or security requirement has the same
        identifier in both documents. Goals are G1 to G6, assumptions A1 to
        A4, business rules BR1 to BR3, likely changes LC, and unlikely
        changes UC. Rows of the Failure Mode and Effects Analysis (FMEA) in
        the Hazard Analysis are written H1.1 to H7.3.
  \item \textbf{Requirement entries.} Each requirement is a statement using
        \emph{shall}, followed by its \emph{Rationale}, a \emph{Fit
        criterion} that says how it will be tested, \emph{Traces to} (the
        goals, use cases, hazards, and requirements it depends on or refines),
        and \emph{Referenced by} (the requirements that trace to it). Every
        requirement identifier in a trace is a link to that requirement, so
        each dependency can be followed in both directions.
  \item \textbf{Symbolic constants} are written in \cn{TYPEWRITER} type and
        defined only in Appendix~\ref{SecConstants}. Field names of the song
        map are also in \texttt{typewriter} type and are defined in the data
        dictionary (Section~\ref{SecDataModel}).
  \item \textbf{Mathematical notation} in Section~\ref{SecFormal}:
        $\langle \ldots \rangle$ is a sequence, $[1..n]$ is the integers from
        1 to $n$, $\mathbb{R}^{+}$ is the positive real numbers, $\varepsilon$
        is the empty string, $\bot$ means \emph{no value}, and $\forall$,
        $\wedge$, $\neg$, and $\equiv$ are \emph{for all}, \emph{and},
        \emph{not}, and \emph{is defined as}. Times are in seconds from the
        start of the audio.
  \item \textbf{Terms} with a specific meaning in this document are defined
        in the glossary (Section~\ref{SecGlossary}), and acronyms are written
        out on first use and listed in Section~\ref{SecAcronyms}.
  \item \textbf{Diagrams} have a legend that explains each shape and arrow.
\end{itemize}

\section{Purpose of the Project}
\subsection{User Business}
Language learners who study on their own at early intermediate to intermediate levels
often use songs to hear vocabulary, idioms, and cultural references as native
speakers use them. Media players and lyrics websites do not support studying
this material. When a learner meets an unfamiliar word, they have to pause the
audio, look the word up in another tool, and copy it into a flashcard
application by hand. This interrupts listening and separates the word from the
lyric that gives it its meaning.

\progname{} combines synchronized lyrics, translations of each line,
transliterations for scripts other than Latin, contextual annotations, and vocabulary
export to Anki in one workflow.

\subsection{Goals of the Project}
The goals below are taken from the Problem Statement and Goals document. Each
goal's measure is refined into the requirements listed in
Table~\ref{TblGoalTrace}.

\begin{itemize}
    \item[G1] \textbf{Synchronized Lesson Playback:} highlight each lyric line
    within \cn{SYNC\_TOL} of its mapped timestamp for at least \cn{SYNC\_PASS}
    of line transitions in the acceptance suite.
    \item[G2] \textbf{Vocabulary Support in Context:} show the translation and
    contextual annotation of every annotated target when it is selected.
    \item[G3] \textbf{Interoperability between Creators and Learners:} a song map created by
    the editor validates against one shared format and opens in the learner app
    without manual changes.
    \item[G4] \textbf{Practical Lesson Creation:} at least \cn{CREATE\_PASS} test
    creators produce a complete map for a test track of at most
    \cn{TEST\_TRACK\_LINES} lines within \cn{CREATE\_TIME}, without editing
    the map file by hand.
    \item[G5] \textbf{Support for Different Writing Systems:} display lyrics correctly for
    \cn{LANG\_COUNT} languages, at least one with a writing system other than Latin,
    with word divisions and transliterations that match the song map.
    \item[G6] \textbf{Vocabulary Retention Handoff:} sending a selected item
    creates an Anki note with correct \emph{Term}, \emph{Translation}, and
    \emph{Context} fields.
\end{itemize}

\subsection{Personas}
Each persona describes a user's goal, what frustrates them today, and how
they feel about it, and names the requirements that respond to them.
\begin{itemize}
    \item \textbf{Kenji (learner):} a Japanese learner at early intermediate
          level who listens to Japanese pop music on the train but cannot read
          kanji at singing speed. Today he pauses the song, copies a word into a
          dictionary, and types it into Anki, and by then the line has passed.
          He feels the song stops being fun as soon as it becomes study. He
          needs to follow the romanized lyrics (FR6), tap a word without
          stopping the music (FR7), and send it to Anki in one tap with the
          lyric line attached (FR8), knowing it was saved (IN8).
    \item \textbf{Elena (creator):} a language tutor who prepares song lessons
          for her students. Today she builds them in slides with no timing,
          and every student has to search the song again. She worries about
          spending an evening on a lesson and losing it, and about using
          songs she does not have the right to share. She needs fast timing by
          tapping along (FR10), autosave and undo (IN6), checks that catch
          mistakes before export (FR14), and licence fields that remind her
          what she may share (LG1).
    \item \textbf{Amara (learner with low vision):} studies Japanese with large
          system text and sometimes uses VoiceOver. Most lyric apps mark the
          current line only with a colour change she cannot see well, and she
          feels excluded by apps that ignore her text size. She needs the
          active line marked by more than colour and text that follows her
          settings (HS5), labelled controls (UH7), and sufficient contrast
          (ST1).
\end{itemize}

\section{Mandated Constraints}
\subsection{Solution Constraints}
The requirements in this document say \emph{what} the product must do and
avoid choosing a design. The few design decisions that are already fixed are
recorded here as constraints, each with its reason. MC1 and MC2 were agreed in
the Development Plan and reviewed by the supervisor before this document was
written. MC3 follows from goal G3.
\begin{itemize}
    \item[\reqdef{MC1}] All application code and the shared song map types shall be
    written in TypeScript.
    \\\textit{Rationale:} one language for the app, editor, and shared code
    lets all three use the same song map types and validator.
    \item[\reqdef{MC2}] The learner app shall be built with React Native and Expo. The
    editor shall be built with React.
    \\\textit{Rationale:} one code base covers iOS and Android, and the editor
    can reuse the app's TypeScript code (Development Plan, Expected
    Technology).
    \item[\reqdef{MC3}] Lessons shall be stored and exchanged as song maps that conform
    to one versioned JSON Schema (a schema for JavaScript Object Notation
    files).
    \\\textit{Rationale:} required by goal G3.
\end{itemize}

\section{Relevant Facts And Assumptions}
\subsection{Relevant Facts} \label{SecFacts}
\begin{itemize}
    \item Japanese is written without spaces between words and mixes kanji,
          hiragana, and katakana. Many kanji have more than one reading, and
          the correct reading depends on the context.
    \item In Anki, a note holds related information in fields, and its note
          type defines those fields and the cards generated from it. Cards
          are organized into decks~\cite{AnkiManual}.
    \item AnkiConnect is an add-on for desktop Anki. By default it accepts
          requests only on \texttt{127.0.0.1}, port 8765, and it can be
          configured to require an API key~\cite{AnkiConnect}.
    \item AnkiDroid provides an application programming interface (API) that other Android apps can use to add
          notes. It requires a permission that Android asks the user to
          grant at runtime~\cite{AnkiDroidAPI}:\\
          \nolinkurl{com.ichi2.anki.permission.READ_WRITE_DATABASE}.
    \item AnkiMobile, the iOS version of Anki, accepts new notes through an
          \nolinkurl{anki://x-callback-url/addnote} URL from version 2.0.30
          onwards~\cite{AnkiMobileURL}. Whether this can confirm that a note
          was created, as IN8 requires, has not been tested.
    \item Mobile operating systems control audio routing, system volume, and
          when background apps are suspended.
\end{itemize}

\subsection{Business Rules} \label{SecRules}
\begin{itemize}
    \item \textbf{BR1 (Open Access):} no user account or payment is required to
          open a song map.
    \item \textbf{BR2 (Schema Adherence):} a song map must pass validation
          (Section~\ref{SecFormal}) before the editor exports it or the learner
          app opens it.
    \item \textbf{BR3 (Copyright Compliance):} the project does not distribute
          audio or lyrics unless they are created by the team, in the public domain,
          or licensed for that use.
\end{itemize}

\subsection{Assumptions}
\begin{itemize}
    \item[A1] Learners have an iOS or Android phone that meets the minimum
    operating system version of the Expo SDK release used.
    \\\textit{Rationale:} the app cannot run on older systems. This is a
    platform limit, not a design choice.
    \item[A2] Creators have the audio and lyric text for the songs they map,
    and the right to use them.
    \\\textit{Rationale:} the editor does not supply content (BR3, LG1).
    \item[A3] Learners who want to export vocabulary have Anki installed on
    the device that receives the notes.
    \\\textit{Rationale:} \progname{} is not a flashcard application. It hands
    vocabulary to Anki (G6).
    \item[A4] Software from other vendors (the operating systems, browsers, Anki,
    AnkiDroid, and AnkiConnect) behaves as described in its documentation.
    \\\textit{Rationale:} defects inside that software are outside the
    team's control. The app must still detect and report a failed handoff
    (IN8).
\end{itemize}

Song maps and their creators are not assumed to be free of errors or trustworthy.
Requirements IN2, IN4, IN5, IM1, and IM2 handle incorrect or malicious song
maps.

\section{The Scope of the Work}
\subsection{The Current Situation}
To study a song today, a learner plays it in a music app, reads the lyrics and
a translation on a separate website, looks up words in a dictionary, and types
useful words into Anki. Creators who want to share a song lesson have no
common format, so each lesson is prepared by hand in documents or slides, and
timing is not recorded.

\section{Business Data Model and Data Dictionary} \label{SecDataModel}
\subsection{Business Data Model}
A \textbf{song map} contains:
\begin{itemize}
    \item \textbf{Metadata:} schema version, title, artist, target language,
          difficulty level, explicit content flag, audio file path, audio
          duration, measured audio loudness, audio and lyric source and
          licence, published flag, and export history.
    \item \textbf{Lyric lines:} start time, end time, original text, line
          translation, and an ordered list of words.
    \item \textbf{Words:} surface text, reading or transliteration,
          optional start and end time, translation, and a verified flag.
    \item \textbf{Annotations:} the word or line range they apply to, a
          contextual explanation, an optional note on register (how formal or
          offensive a term is), the name of the author, and the name of the
          reviewer.
\end{itemize}

\begin{itemize}
    \item \textbf{PUC1 (Play synchronized lesson):} the learner opens a
          song map package. The app validates it and shows the lesson. The

          times, reviews the suggested segmentation and readings, enters

\section{Formal Specification} \label{SecFormal}

This section defines a valid song map, the line that is active at a given
audio position, and the learner app's playback modes. Constants are listed in
Appendix~\ref{SecConstants}.

\subsection{Song Map}
A song map is a tuple $S = (v, d, L, N)$ where $v = (v_{\mathit{maj}},
v_{\mathit{min}}, v_{\mathit{pat}})$ is the schema version, $d \in
\mathbb{R}^{+}$ is the audio duration in seconds, $L = \langle \ell_1, \ldots,
\ell_n \rangle$ is the sequence of lines, and $N$ is the set of annotations.
Each line is $\ell_i = (s_i, e_i, W_i)$ with start time $s_i$, end time $e_i$,
and words $W_i = \langle w_{i,1}, \ldots, w_{i,m_i} \rangle$. A word
$w_{i,j}$ has a verified flag $\mathit{ver}_{i,j}$ and optional times
$s_{i,j}, e_{i,j}$. An annotation $a \in N$ has a translation
$a.\mathit{tr}$, a note $a.\mathit{note}$, an author $a.\mathit{auth}$, and a
reviewer $a.\mathit{rev}$.

$S$ is valid, written $\mathit{valid}(S)$, when all of conditions V1 to V8
hold:
\begin{description}
\item[V1] (version) $v_{\mathit{maj}} \in \cn{SUPPORTED\_MAJOR}$ (IN3).
\item[V2] (at least one line) $n \ge 1$.
\item[V3] (lines inside the audio) $\forall i \in [1..n] : 0 \le s_i < e_i
\le d$.
\item[V4] (lines ordered, no overlap) $\forall i \in [1..n-1] : e_i \le
s_{i+1}$.
\item[V5] (words inside their line) for every word $w_{i,j}$ that has times,
$s_i \le s_{i,j} < e_{i,j} \le e_i$.
\item[V6] (segmentation verified) $\forall i, j : \mathit{ver}_{i,j}$ (IN4).
\item[V7] (annotations complete) $\forall a \in N : a.\mathit{tr} \neq
\varepsilon \wedge a.\mathit{note} \neq \varepsilon$.
\item[V8] (audio reference and limits) the audio path is relative and
resolves inside the package (IM2),
$|d - d_{\mathit{audio}}| \le \cn{AUDIO\_DUR\_TOL}$ (IN11), the map size is
at most \cn{MAX\_MAP\_SIZE}, and its nesting depth is at most
\cn{MAX\_NESTING} (IM1).
\end{description}
Here $d_{\mathit{audio}}$ is the duration of the decoded audio file and
$\varepsilon$ is the empty string. The JSON Schema~\cite{JSONSchema2020}
checks structure and types. The shared validator checks the remaining
conditions (FR16).

A valid map may be marked as published only when every annotation has a
reviewer other than its author (IN5):
\[
\mathit{publishable}(S) \equiv \mathit{valid}(S) \wedge \forall a \in N :
a.\mathit{rev} \neq \varepsilon \wedge a.\mathit{rev} \neq a.\mathit{auth}.
\]

\subsection{Active Line and Synchronization}
For an audio position $p$, the active line is
\[
\mathit{active}(p) =
\begin{cases}
i & \text{if } s_i \le p < e_i\\
\bot & \text{if no line satisfies } s_i \le p < e_i
\end{cases}
\]
which is well defined because valid lines do not overlap. Let $h_i$ be the
audio position at which the learner app changes the highlight to line $i$.
A transition is on time when $|h_i - s_i| \le \cn{SYNC\_TOL}$. FR4 requires
that, over all transitions in the acceptance suite,
\[
\frac{|\{ i : |h_i - s_i| \le \cn{SYNC\_TOL} \}|}{\text{number of transitions}}
\ \ge\ \cn{SYNC\_PASS}.
\]

\subsection{Playback Modes}
The learner app is in one of the modes \textit{NoLesson}, \textit{Ready},
\textit{Playing}, and \textit{Paused}. The initial mode is \textit{NoLesson}.
Table~\ref{TblModes} gives the transitions. Events not listed for a mode leave
the mode unchanged. In \textit{Playing} and \textit{Paused}, the highlighted
line is $\mathit{active}(p)$, where $p$ is the position reported by the audio
player.

\subsubsection*{Intended Data Flow and Privacy Obligations}
The initial release is designed so that the team does not receive any
personal data. The intended data flow is:
\begin{itemize}
    \item The learner's lessons, display preferences, and queue of vocabulary
          waiting for Anki are stored only on the learner's device (IN8, UH3).
    \item Vocabulary leaves the app only when the learner sends it to Anki.
          The note goes to Anki on the same device, or to desktop Anki through
          AnkiConnect, and is then stored in the learner's own Anki collection.
          What happens to the collection after that, including synchronization
          through AnkiWeb, is controlled by the learner and Anki, not by
          \progname{}.
    \item Error reports leave the device only through the share sheet, to a
          destination the learner chooses (AU1).
    \item Song maps contain the names of the creators and reviewers (AU2, IN5),
          and these names are distributed with each map.
    \item The editor stores drafts in the creator's browser storage (IN6).
\end{itemize}

This data flow limits the product's privacy obligations, but does not remove
them: the app stores vocabulary history on the device, it writes into the
learner's Anki collection, and song maps carry creators' names. The team has
not yet determined which privacy laws and platform policies apply. Before the
app is distributed outside the team and test participants, the team shall
confirm this, including Canadian privacy law and the privacy disclosures
required by the Apple App Store and Google Play, and shall check it again
whenever the data flow changes (see Open Issues).

\section{Open Issues}
\begin{itemize}
    \item \textbf{Anki handoff method.} Whether the learner app uses the
          AnkiDroid API, AnkiConnect, an export file, or a combination
          depends on the PoC (risk R3). On iOS, AnkiMobile's
          \texttt{addnote} URL scheme~\cite{AnkiMobileURL} is a candidate,
          but whether it can confirm that a note was created (IN8) has not
          been tested. Affects OE2, AC2, PR2, IN8 to IN10.
    \item \textbf{Mobile timing accuracy.} Whether Expo Audio reports position
          accurately enough for FR4 depends on the PoC (risk R1).
    \item \textbf{Second language.} Japanese is the language whose writing system is not Latin. The
          second language for G5 has not been chosen.
    \item \textbf{Japanese tokenizer.} kuromoji.js is the current choice for
          FR11. Sudachi is more accurate but needs a separate service. Because
          segmentation runs in the editor (IN4), either is possible.
    \item \textbf{Lesson distribution.} The initial release moves song map
          packages as files. Whether lessons should also be bundled with the
          app for the demonstration is undecided.
    \item \textbf{Loudness target.} HS9 measures loudness with ITU-R
          BS.1770. The values of \cn{TARGET\_LOUDNESS} and
          \cn{LOUDNESS\_TOL} are initial and will be confirmed with the
          acceptance suite tracks. Whether the editor should also normalize
          the audio, rather than only warn, is undecided.
    \item \textbf{Privacy obligations.} The privacy laws and app store privacy
          disclosures that apply to the intended data flow (Compliance
          Requirements) have not been confirmed. This must be done before the
          app is distributed outside the team and test participants.
\end{itemize}

\section{Off-the-Shelf Solutions}

    \item \textbf{Musixmatch}~\cite{Musixmatch}: a lyrics service that shows

          by creators.

The LRC lyric file format stores lines as \texttt{[mm:ss.xx] text}, and its
extended form adds word timestamps. The song map's timing fields can follow the
same model, and the editor may import LRC files in a later release
(stretch goal: song map import and export).

\section{New Problems}
\subsection{Effects on the Current Environment}
Learners will move some song study from several separate tools into one app.
Creators will need to record licence information they may not have recorded
before (LG1).

\subsection{Effects on the Installed Systems}
The learner app adds notes to the learner's Anki collection and may create a
\progname{} deck and note type (AC1). If AnkiConnect is used, the learner must
change its configuration (AC2).

\subsection{Potential User Problems}
\begin{itemize}
    \item Learners may import songs they do not have the right to use. The
          product cannot prevent this for personal files (BR3 applies only to
          content the project distributes).
    \item Learners may rely on transliteration and not learn to read the
          original script. UH3 lets them hide it.
    \item Learners may use the app while moving (HS3).
\end{itemize}

\subsection{Limitations in the Anticipated Implementation Environment That May
Inhibit the New Product}
\begin{itemize}
    \item The interval at which Expo Audio reports playback position limits
          highlight accuracy (risk R1).
    \item iOS does not provide a confirmed way for another app to add notes to
          Anki directly (OE2).
    \item Mobile operating systems may suspend apps in the background, which
          affects highlight alignment after return (IN1).
\end{itemize}

\subsection{Follow-Up Problems}
Changes to the song map schema after lessons are published will require older
maps to remain readable (LO1) or a conversion tool (stretch goal).

\section{Migration to the New Product}
\subsection{Requirements for Migration to the New Product}
\progname{} is a new product and does not replace a deployed application, so
no user accounts, lesson libraries, or other data need to be migrated for the
initial release.

Creators produce new song maps with the editor, and learners open song maps
that conform to the shared, versioned JSON Schema. Later versions may add
import or conversion tools if an earlier schema version or an external lesson
format must be supported.

\subsection{Data That Has to be Modified or Translated for the New System}
No existing data must be converted for the initial release. Each lesson is
authored directly in the song map format and validated before use.

If the schema's major version changes in a later release, a reader for the old
version or a documented conversion process will be required so that existing
valid maps remain usable (LO1). Translation, transliteration, timing, and
annotation data are stored as explicit song map fields and do not need
conversion in the initial release.

\section{Ideas for Solution}
The proposed solution consists of a mobile learner app, a song map editor that runs in a web browser, and a shared TypeScript core. The learner app plays lesson audio,
displays synchronized lyric lines, shows translations, transliterations, and
annotations, and sends selected vocabulary to Anki. The editor creates and
validates song maps without requiring creators to edit JSON files.

A versioned JSON Schema defines the song map, including metadata, timed lyric
lines, words, translations, transliterations, and annotations. Using one
validated format lets lessons created in the editor open in the learner app
without changes.

The current implementation direction is React Native with Expo for the learner
app, React for the editor, and TypeScript for the shared schema and validation
logic. Japanese segmentation and romanization may use kuromoji.js in the
editor. These are implementation ideas, not requirements. Other technologies
may be used if the requirements and constraints are met.
